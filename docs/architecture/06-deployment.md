# 06. Развёртывание

## Образы

| Образ | Содержимое | Примерный размер |
|---|---|---|
| `notes-app` | Python, aiogram, SQLAlchemy, RQ, trafilatura, httpx | ~400 МБ |
| `notes-app-heavy` | `notes-app` + ffmpeg, yt-dlp, faster-whisper, веса `small` | ~1.5 ГБ |
| `notes-embeddings` | FastAPI, sentence-transformers, torch CPU, веса модели | ~2.5 ГБ |

Размеры - оценка порядка величины, это моё предположение; точные цифры
будут известны после первой сборки.

Разделение `app` и `app-heavy` сделано ради того, чтобы под бота не тащил
полтора гигабайта зависимостей, которые ему не нужны, и запускался за
секунды, а не за минуту. Оба собираются из одного Dockerfile разными
таргетами multi-stage, так что общий код не дублируется.

Веса моделей Whisper и embedding запекаются в образ на этапе сборки.
Альтернатива - PVC с прогревом - даёт меньший образ, но вводит состояние в
то, что должно быть stateless, и усложняет откат. Для трёх подов это не
оправдано.

## Единицы развёртывания

| Объект | Вид | Реплики | requests | limits |
|---|---|---|---|---|
| `notes-bot` | Deployment, strategy `Recreate` | ровно 1 | 100m / 256Mi | 500m / 512Mi |
| `notes-worker-fast` | Deployment | 1-2 | 200m / 512Mi | 1 / 1Gi |
| `notes-worker-heavy` | Deployment | 1 | 500m / 1.5Gi | 2 / 3Gi |
| `notes-embeddings` | Deployment + Service | 1-2 | 500m / 1Gi | 1500m / 2.5Gi |
| `notes-gc` | CronJob, `0 3 * * *` | - | 100m / 256Mi | 500m / 512Mi |
| `notes-migrate` | Job, руками или в пайплайне | - | 100m / 256Mi | 500m / 512Mi |

Значения ресурсов - стартовая оценка, это моё предположение; корректировать
по факту после первой недели работы. Особенно `notes-worker-heavy`: реальный
профиль памяти Whisper надо померить, а не угадывать. Голосовые заметки
добавляют к этой очереди поток коротких задач - если они окажутся частыми,
вторая реплика тяжёлого воркера понадобится раньше, чем расчёт только на
Instagram.

### Почему у бота ровно одна реплика

Long polling через `getUpdates` не допускает двух одновременных потребителей
на одном токене: Telegram отдаст апдейты произвольному из них, и часть
сообщений будет обработана не тем процессом либо потеряна. Отсюда
`replicas: 1` и `strategy: Recreate` - при `RollingUpdate` старый и новый
поды на короткое время сосуществуют, чего допускать нельзя.

Если понадобится больше одной реплики или обновление без даунтайма, нужен
переход на webhook с Ingress и TLS. Для текущих требований это не оправдано,
но развилка зафиксирована в ADR-11.

### Почему тяжёлый воркер отдельно

Транскрибация - минуты CPU и гигабайты RAM. Через эту очередь проходят и
аудио из Instagram, и голосовые заметки пользователя. В общем воркере
транскрибация заблокирует сохранение обычной текстовой заметки на всё это
время. Отдельный деплоймент
даёт независимые лимиты, независимое масштабирование и возможность падать,
не задевая быстрый путь.

`notes-worker-fast` слушает очереди `fast` и `llm` в таком порядке -
пользовательские задачи имеют приоритет над обогащением.

## Health-пробы

| Компонент | liveness | readiness |
|---|---|---|
| `notes-bot` | HTTP `/healthz` на служебном порту | тот же, плюс успешный `getMe` |
| воркеры | наличие процесса и свежий heartbeat в Redis | - |
| `notes-embeddings` | `/healthz` | `/readyz` - только после прогрева модели |

У embedding-сервиса `readinessProbe` обязана иметь запас по
`initialDelaySeconds` и `failureThreshold`: загрузка модели с диска занимает
десятки секунд, и под не должен быть перезапущен за то, что он ещё грузится.
`startupProbe` предпочтительнее - он снимает ограничение с liveness на время
старта.

## Graceful shutdown

- **Бот**: по SIGTERM останавливает polling, доигрывает текущий апдейт,
  закрывает сессии. `terminationGracePeriodSeconds: 30`.
- **Воркеры**: RQ по SIGTERM даёт задаче доработать. Для `heavy` период
  ожидания должен быть больше типичной задачи, иначе транскрипция будет
  обрываться при каждом деплое. `terminationGracePeriodSeconds: 600`,
  задача идемпотентна и при обрыве переставится заново.

## Секреты и сеть

- `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`, `REDIS_URL`, `PROXY_AI_URL` - в
  Secret, монтируются переменными окружения.
- Отдельная роль в Postgres для этого бота, отдельная схема или как минимум
  отдельные права. База общая с family-bot, и права не должны пересекаться.
- Отдельный номер базы Redis, чтобы ключи не конфликтовали с существующими.
- NetworkPolicy: `notes-embeddings` принимает трафик только от подов бота и
  воркеров, наружу не выставляется.
- Исходящий трафик к произвольным сайтам идёт только из воркеров. Бот во
  внешний интернет ходит только в Telegram API. Это уменьшает поверхность
  SSRF, описанного в `03-ingest.md`.

## Миграции

Отдельный Job с `alembic upgrade head`, запускается до обновления подов.
Автоматический запуск миграций в initContainer каждого пода недопустим: при
нескольких подах они пойдут параллельно.

Правило совместимости: миграция должна быть совместима с предыдущей версией
кода, чтобы порядок «сначала миграция, потом деплой» всегда работал. Удаление
колонок делается в два релиза - сначала код перестаёт их использовать, потом
колонка удаляется.

## Наблюдаемость

Логи - structlog в JSON, обязательные поля: `note_id`, `user_id`, `chat_id`,
`job_id`, `source_type`, `duration_ms`. Токен бота, содержимое заметок и
тексты запросов в логи не пишутся - это персональные данные.

Метрики, которые понадобятся с первого дня:

| Метрика | Зачем |
|---|---|
| Длина очередей `fast`, `heavy`, `llm` | Раньше всего показывает, что воркер не справляется |
| Время обработки по `source_type` | Отдельно покажет реальную стоимость Whisper |
| Доля `status='failed'` и `enrich_status='failed'` | Здоровье экстракторов и proxy-ai |
| Латентность `/search` p50 / p95 | Дизайн-док требует, чтобы обычный поиск был быстрым |
| Латентность `/embed` | Узкое место общее для приёма и поиска |
| Доля ошибок yt-dlp по источникам | Сигнал, что Instagram или YouTube начали блокировать |

Последняя метрика заслуживает алерта: блокировки внешних площадок - самый
вероятный вид поломки в этой системе, и узнать о ней лучше из графика, чем
из жалобы пользователя.

## Резервное копирование

Отдельного бэкапа не требуется - Postgres общий с family-bot и наследует его
политику. Проверить нужно одно: что дамп включает расширение `vector` и
восстанавливается вместе с ним.
