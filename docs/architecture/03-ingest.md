# 03. Пайплайн приёма заметки

## Общий поток

```mermaid
sequenceDiagram
    participant U as Пользователь
    participant B as notes-bot
    participant PG as Postgres
    participant Q as Redis / RQ
    participant W as Worker
    participant E as embeddings
    participant AI as ai-proxy (codex)

    U->>B: сообщение
    B->>B: классификация источника
    B->>PG: INSERT note (status=pending, visibility=private)
    B->>Q: enqueue process_note(note_id) в fast|heavy
    B-->>U: "Сохраняю..." + кнопки приватности
    Note over U,B: пользователь может переключить приватность в любой момент

    W->>PG: UPDATE status=processing
    W->>W: extract (сеть, медиа, whisper)
    W->>W: chunk
    W->>E: POST /embed kind=passage
    E-->>W: векторы
    W->>PG: транзакция: DELETE chunks + INSERT chunks + status=done
    W->>Q: enqueue enrich_note(note_id) в llm
    W-->>B: уведомление о готовности
    B-->>U: карточка заметки

    W->>AI: title / tags / structured / summary / dupes
    W->>PG: UPDATE обогащение, enrich_status=done
```

Ключевое: заметка попадает в БД до начала обработки. Если воркер упадёт, сеть
отвалится или Whisper не справится - у пользователя всё равно сохранён
исходный текст или ссылка. Потеря данных из-за отказа внешнего сервиса
исключена по построению.

## Шаг 1. Классификация источника

Выполняется в боте, синхронно, без сети.

```
тип сообщения Telegram?
├── voice                                     → voice
└── текстовое: есть URL в тексте?
├── нет                                       → text
└── да, берём первый URL
    ├── host ∈ {youtube.com, youtu.be, m.youtube.com}      → youtube
    ├── host ∈ {instagram.com, www.instagram.com}          → instagram
    ├── host ∈ короткие ссылки карт
    │        {maps.app.goo.gl, goo.gl/maps, maps.google.*}  → map
    └── иначе                                               → page
```

Если в сообщении есть и URL, и собственный текст пользователя, сохраняется и
то и другое: URL в `source_url`, весь текст сообщения в `raw_text`. В индекс
пойдут оба - комментарий пользователя часто содержательнее автоизвлечённого
текста.

Прочие ссылки внутри описаний постов и видео не обходятся - остаются текстом
внутри заметки, как задано дизайн-доком.

## Шаг 2. Приём в боте

```
1. Проверить, надо ли вообще сохранять (для групп - capture_mode, ADR-10)
2. INSERT ... ON CONFLICT (chat_id, tg_message_id) DO NOTHING RETURNING id
   - конфликт означает повторную доставку, ничего не делаем
3. Для личного чата: visibility = user_settings.default_visibility (дефолт 'private')
   Для группы: visibility = NULL
4. Выбрать очередь: instagram и voice → heavy, всё остальное → fast
5. enqueue с job_id = f"process_note-{note_id}" - защита от двойной постановки
   (дефис, не двоеточие: RQ 2.x запрещает в job_id всё, кроме `[A-Za-z0-9_-]`)
6. Ответить пользователю сразу, не дожидаясь обработки
```

Ответ бота в личном чате содержит инлайн-кнопки `🔒 приватная` /
`🌐 публичная`. Кнопка это переключатель уже проставленного значения, а не
блокирующий шаг: обработка идёт параллельно, пока пользователь думает.
Переключение приватности не трогает чанки и векторы - это `UPDATE` одной
колонки.

## Шаг 3. Экстракторы

Единый интерфейс:

```python
class Extractor(Protocol):
    source_type: str
    queue: Literal["fast", "heavy"]

    async def extract(self, note: Note) -> ExtractResult: ...

@dataclass
class ExtractResult:
    text: str                 # то, что пойдёт в extracted_text
    title: str | None         # техническое название из источника, не LLM-заголовок
    lang: str | None
    meta: dict                # длительность, автор, наличие субтитров и т.п.
```

| Тип | Инструмент | Что делает | Очередь |
|---|---|---|---|
| `text` | - | Возвращает пустой результат, индексируется `raw_text` | fast |
| `voice` | Bot API `getFile` + ffmpeg + `faster-whisper` | Скачивает голосовое сообщение, транскрибирует. Подпись к голосовому, если была, попадает в `raw_text` | heavy |
| `page` | `trafilatura` | Забирает страницу через SSRF-safe фетчер, извлекает основной текст | fast |
| `youtube` | `yt-dlp` (metadata-only) + `youtube-transcript-api` | Заголовок, описание, субтитры при наличии. Распознавание речи не применяется | fast |
| `instagram` | `yt-dlp` + ffmpeg + `faster-whisper` | Caption поста, затем аудиодорожка, затем транскрипт. Конкатенация обоих | heavy |
| `map` | HTTP HEAD/GET без тела | Следует за редиректом, из финального URL достаёт имя места. Страница не скрапится | fast |

### SSRF-safe фетчер

Пользователь диктует URL, а бот живёт внутри кластера. Без защиты бот
превращается в инструмент разведки внутренней сети. Обязательные меры для
всех исходящих запросов по пользовательским URL:

- разрешены только схемы `http` и `https`;
- DNS резолвится заранее, адрес проверяется против блок-листа: loopback,
  link-local (`169.254.0.0/16`, включая `169.254.169.254`), RFC1918,
  `::1`, unique-local IPv6, метаданные облака;
- соединение идёт на проверенный IP с явным `Host`-заголовком - иначе DNS
  можно перепривязать между проверкой и запросом;
- каждый редирект проверяется заново, максимум 5 переходов;
- таймаут на соединение и на общую длительность;
- жёсткий лимит размера тела, чтение потоком с обрывом по превышению;
- ограничение Content-Type для `page` (`text/html`, `text/plain`).

Тот же фетчер используется резолвером карт.

### Ограничения тяжёлого пути

| Параметр | Значение | Причина |
|---|---|---|
| Максимальный размер загрузки | 100 МБ | Диск пода и время |
| Максимальная длительность аудио | 20 минут | CPU-время Whisper |
| Максимальный размер файла из Telegram | 20 МБ | Жёсткий лимит Bot API на скачивание |
| Таймаут задачи `heavy` | 30 минут | Не держать воркер вечно |
| Модель Whisper | `small`, `compute_type=int8` | CPU-only, компромисс скорость/качество |
| Временные файлы | `emptyDir`, удаление в `finally` | Под может перезапуститься |

Транскрибация на CPU заметно медленнее реального времени (это моё
предположение - точный множитель зависит от конкретного узла и требует
замера на первом же проде). Если замер покажет неприемлемое время, варианты
по убыванию предпочтительности: модель `base` вместо `small`, ограничение
длительности до 10 минут, отключение транскрипции для длинных постов с
пометкой в карточке заметки.

### Голосовые заметки

Голосовое сообщение боту сохраняется как заметка с `source_type='voice'`:
файл скачивается через Bot API, транскрибируется тем же `faster-whisper`,
что и аудио из Instagram, транскрипт попадает в `extracted_text` и
индексируется. Подпись к голосовому, если она есть, сохраняется в
`raw_text` и тоже идёт в индекс.

Особенности по сравнению с Instagram:

- файл берётся из Telegram, а не скачивается из интернета - SSRF-фетчер и
  `yt-dlp` не участвуют, но действует лимит Bot API на скачивание в 20 МБ;
- длительность обычно секунды или минуты, а не десятки минут, поэтому вклад
  в загрузку очереди `heavy` заметно меньше, чем у видео;
- в личном чате кнопки приватности работают как для любой другой заметки;
- в группе голосовое попадает в бота только как ответ на его сообщение либо
  при включённом режиме `all` - см. ADR-10.

Бот отвечает на голосовое распознанным текстом, чтобы пользователь сразу
видел, что именно уйдёт в индекс.

### Деградация

Экстрактор упал или вернул пустоту - это не провал заметки:

```
extract() успешен и текст непустой  → extracted_text = результат
extract() упал или текст пустой     → extracted_text = NULL,
                                      error = краткая причина,
                                      индексируем raw_text (текст + URL)
                                      status = 'done', а не 'failed'
```

`status='failed'` ставится только если не удалось даже посчитать эмбеддинг
для `raw_text` - то есть заметку физически нельзя найти. Пользователю в этом
случае приходит сообщение с возможностью повтора (`render.render_processing_failed`,
отправляется тем же `sender`, что и `/debug`-уведомление, прямо из воркера) -
без текста ошибки, он только в ops-алерте (`clients/alerts.py`), не в чате
пользователя.

## Шаг 4. Чанкинг

```
1. Нормализация: схлопывание пробелов, удаление служебных таймкодов субтитров,
   удаление повторяющихся строк (типично для автосубтитров YouTube)
2. Разбиение по абзацам, затем по предложениям
3. Сборка чанков до целевого размера в токенах с перекрытием
4. Отбрасывание чанков короче минимального порога, кроме случая
   "у заметки всего один чанк"
```

Параметры:

| Параметр | Значение | Обоснование |
|---|---|---|
| Целевой размер чанка | 400 токенов | Помещается в контекст обеих моделей-кандидатов |
| Перекрытие | 60 токенов | Мысль на границе чанков не теряется |
| Минимальный чанк | 40 токенов | Обрывки дают шумные векторы |
| Максимум чанков на заметку | 200 | Защита от часового транскрипта |

Токенизация выполняется тем же токенайзером, что и у активной модели, -
`embeddings` отдаёт его имя через `GET /model`. Считать чанки в символах
нельзя: для иврита и кириллицы соотношение символов к токенам сильно
отличается от английского.

Отдельное замечание по выбору модели: у `paraphrase-multilingual-mpnet-base-v2`
длина входа заметно меньше, чем у `intfloat/multilingual-e5-base` (это моё
предположение, нужно проверить по `max_seq_length` при бенчмарке на M1).
Если оно подтвердится, целевой размер чанка придётся опустить под первую
модель или выбрать вторую. Это входит в план замера на этапе M1.

## Шаг 5. Эмбеддинг и запись

```python
# в одной транзакции
DELETE FROM note_chunks WHERE note_id = :id;
INSERT INTO note_chunks (note_id, chunk_index, chunk_text, token_count,
                         embedding, embedding_model)
VALUES ...;
UPDATE notes SET status='done', extracted_text=..., lang=..., updated_at=now()
WHERE id = :id;
```

Вызов embedding-сервиса идёт до открытия транзакции - сеть не должна
удерживать блокировки. Батч ограничен по количеству текстов и по суммарной
длине.

Перед вызовом текст каждого чанка (лучше-эффорт) переводится на общий
язык через notes-translate - см. `04-search.md`, "Перевод перед
эмбеддингом", и `05-contracts.md`, "Translate-сервис". `chunk_text`,
записанный в `note_chunks` (строка выше), - всегда исходный,
непереведённый текст; переводу подвергается только то, что уходит в
`embed_passages`.

### Debug: время обработки

Временная диагностическая команда `/debug` (`user_settings.debug_enabled`,
по умолчанию выключено) - переключает личный флаг пользователя. Когда
включён, `process_note` при успешном завершении (только успех, не при
`status='failed'`) сам, из воркера, шлёт в тот же чат отдельное сообщение
"⏱ Обработка завершена. Заняло: N.Nс" плюс краткое описание того, что было
в заметке - тем же способом, каким `smart_answer` шлёт готовый ответ
(`TelegramSender`, прямой вызов Bot API из воркера, не через диспетчер
бота). Время считается от начала экстракции до записи чанков включительно -
`enrich_note` (обогащение) в него не входит, он и так асинхронный и не
блокирует `status='done'`.

Описание - это не готовый `notes.summary` (на этот момент он ещё не
существует: `enrich_note` только поставлен в очередь и выполнится позже), а
отдельный, синхронный внутри `process_note` вызов `enrich.generate_summary`
над тем же `text`, что пошёл в `chunk()` и эмбеддинг. Смысл - не просто
подтвердить, что проиндексировался реальный контент, а сразу сказать, о чём
он был ("это было видео о том, как женщина ищет мужа"), не заставляя
владельца самого пересматривать ссылку. Вызов best-effort: обёрнут в
try/except после того, как `status='done'` уже закоммичен, так что таймаут
или ошибка ai-proxy (`LLMServiceError`, включая `quota_exhausted`) не
блокирует и не проваливает обработку заметки - в этом случае (или когда
`LLM_ENABLED=false`) отправляется прежнее превью: первые ~150 символов
`text` как есть.

Ради чего: субъективно оценить, сколько реально занимает обработка ссылки
end-to-end, без необходимости лезть в логи или метрики. Ожидается, что
команда будет выключена (`/debug` ещё раз), как только вопрос закрыт - это
не постоянная фича продукта.

Помимо общего времени, сообщение разбивает его по стадиям
(`render.render_stage_timings`): `extract` (экстракция), `chunk`
(чанкинг), `translate` (перевод перед эмбеддингом, только если
`TRANSLATE_ENABLED=true` - см. `04-search.md`), `embed` (запрос к
embedding-сервису), `save` (запись чанков + `mark_done` + commit). Стадия,
которая в этом прогоне не выполнялась (`translate` при выключенном
переводе), в сообщении просто отсутствует - не показывается как `0.00с`,
что было бы ложным "стадия отработала мгновенно".

## Шаг 6. Обогащение через ai-proxy

Отдельная задача в очереди `llm`, отдельный статус. Никогда не блокирует
`status='done'`: заметка находится поиском ещё до появления тегов. Контракт
ai-proxy - в `05-contracts.md` (провайдер `codex`, `output_format="text"`,
`timeout_s` из `LLM_ENRICH_TIMEOUT_S`).

| Фича | Вход | Выход |
|---|---|---|
| Заголовок | Первые ~1500 токенов текста | `notes.title` |
| Автотеги | То же | `notes.tags` |
| Структурные поля для мест | Текст + признак `source_type='map'` | `notes.structured` |
| Места из видео | Текст + признак `source_type` ∈ {`youtube`, `instagram`} | `notes.structured.places` |
| Суммаризация | Полный текст, если он длиннее порога | `notes.summary` |
| Детекция дублей | Кандидаты, найденные векторным поиском среди своих заметок | Уведомление пользователю |

### Места из видео

Видео (YouTube/Instagram) часто называют конкретные места - ресторан,
адрес - но не всегда текстом: у Instagram-геометки на кадре нет
отдельного текстового поля в ответе yt-dlp (`location` пуст), значит
единственный способ узнать место - то, что реально сказано вслух или
написано в caption. `enrich.generate_places` извлекает все места, сколько
бы их ни упоминалось (`{name, location_hint}`), из caption + ASR-транскрипта
тем же LLM-вызовом,
что и остальное обогащение - никакого OCR по кадрам видео нет.

Следствие: точность ограничена тем, что попало в текст. Название и адрес
могут быть искажены ASR (реальный пример: "Кахетинское шоссе" услышано
как "Пехетинское шоссе"), а если место только на графической геометке и
никогда не произносится - оно не попадёт в `structured` вовсе. Ссылка на
Google Maps (`render.render_places`) строится как поиск по тексту
(`maps.google.com/search?query=...`), не по координатам - без OCR
координат просто нет, и текстовый поиск - штатный способ Google дать
ссылку без геокодирования на своей стороне.

Места показываются только там, где заметка вообще попадает в выдачу: в
карточке `/search` (`render_search_card`) и в списке «Источники» под
ответом `/smart_search` - см. "/smart_search" в 04-search.md.

Детекция дублей построена двухфазно: сначала дешёвый векторный поиск по
заметкам того же владельца отбирает несколько ближайших, и только они
отправляются в LLM на подтверждение. Прогонять через LLM все заметки
нереально.

При недоступности proxy-ai задача ретраится с экспоненциальной задержкой,
после исчерпания попыток - `enrich_status='failed'`. Заметка остаётся
полностью рабочей, просто без заголовка и тегов; их можно догенерировать
позже повторным прогоном.

## Редактирование

Разрешено только для `source_type='text'`, как задано дизайн-доком.
Голосовая заметка под это правило не подпадает: её содержимое - это
автоматически полученный транскрипт, а не то, что пользователь напечатал.
Если на практике окажется, что транскрипты часто требуют правки, правило
можно будет расширить на `voice` без изменений в схеме - `raw_text` там уже
свободен.

```
Текст:
  пользователь присылает новое сообщение как замену
  → UPDATE notes SET raw_text=..., status='pending', updated_at=now()
  → enqueue process_note → полный ре-чанкинг и ре-эмбеддинг
  → enqueue enrich_note  → перегенерация тегов и заголовка

Приватность:
  → UPDATE notes SET visibility=... - мгновенно, векторы не трогаются
```

Во время ре-обработки заметка временно уходит из выдачи (`status != 'done'`).
Это осознанный компромисс в пользу того, чтобы не показывать текст, не
соответствующий векторам.

В группе редактирование обрабатывается той же логикой захвата, что и новое
сообщение (`on_group_message_edited`, тот же `should_capture_group_message`)
- не только `edit_note_by_message` для уже сохранённой заметки. Найдено
живьём: участник добавил `@меншен` бота, отредактировав уже отправленное
сообщение, а не написав новое - Telegram шлёт это как `edited_message`, и до
исправления в группах не было обработчика этого типа апдейта вообще
(только для личных чатов), так что правка молча терялась.

## Удаление и восстановление

```
/list или кнопка в выдаче → подтверждение (Да / Отмена)
  → UPDATE notes SET deleted_at = now() WHERE id=:id AND user_id=:me AND deleted_at IS NULL
/trash → список своих удалённых
  → ♻️ → UPDATE notes SET deleted_at = NULL WHERE id=:id AND user_id=:me
```

`user_id = :me` стоит прямо в `WHERE`, а не проверяется отдельным `SELECT`.
Проверка права и изменение - одна операция, состояния гонки нет. Ноль
затронутых строк означает отказ в доступе.

Hard-delete - CronJob:

```sql
DELETE FROM notes
WHERE deleted_at IS NOT NULL
  AND deleted_at < now() - interval '30 days';
```

Удаление пачками по несколько тысяч строк, чтобы не держать длинную
транзакцию на общем инстансе Postgres. Чанки уходят каскадом.

## /events_table

Разбор скриншотов таблицы (обычно школьное расписание - экзамены,
каникулы, мероприятия) в отдельные заметки, по одному событию на заметку.
Работает в обоих типах чатов.

```
пользователь: альбом скриншотов + подпись "/events_table <название таба>"
  → бот (handlers.on_events_table_photo): буферизует альбом in-process
    (единственная реплика бота, см. cli/bot.py - без Redis не обойтись бы
    при >1 реплике), с debounce 2с после последнего фото - Telegram не
    сообщает, когда альбом закончился
  → скачивает фото через TelegramFileClient, кодирует в base64
  → enqueue parse_events_table в очередь `llm` (не срочно, как
    smart_answer - см. 06-deployment.md)
  → воркер (queue/tasks.py:parse_events_table_async): один вызов
    LLMClient.complete(images=...) с provider, форсированным на
    claude_code - codex отвечает 400 unsupported_image_input на любой
    запрос с images, проверено вживую (05-contracts.md, "Порт LLMClient")
  → результат кладётся в PendingEventsCache (Redis, TTL 30 минут, тот же
    паттерн, что SearchSessionCache) - превью с кнопками [Сохранить]
    [Отмена] шлётся тем же TelegramSender, что и /smart_search
  → "Сохранить" (bot/logic.py:confirm_events_table): по одной заметке
    source_type='table_event' на событие, enqueue process_note как обычно
```

Классификация события (`exam`/`holiday`/`event`) и общие теги таба
("школа" и т.п.) - всё определяет LLM по смыслу текста, не по цвету
заливки ячеек: живые примеры таких таблиц показали, что цвет используется
непоследовательно и не совпадает даже с собственной легендой листа. Текст
заметки - `"{дата}: {текст события}"` (или `"{дата}–{дата}: ..."` для
многодневного, например праздника), теги - тип события плюс тема таба
(`NoteRepository.set_tags_and_skip_enrich`) - `enrich_note` для этих
заметок не запускается вовсе (`process_note_async` пропускает постановку
в очередь `llm` для `source_type='table_event'`), иначе он переписал бы
уже готовые теги собственной догадкой по одной короткой строке текста, без
знания темы всей таблицы.

`table_event` не имеет экстрактора - его текст уже финальный на момент
создания заметки, поэтому `_extract_and_get_index_text` обрабатывает его
как `'text'`: `raw_text` идёт в чанкинг и эмбеддинг как есть.

## Импорт экспорта Telegram

Bot API не даёт истории до момента добавления бота - это ограничение
платформы. Одноразовый скрипт `tools/import_telegram_export.py`:

```
result.json (Telegram Desktop export)
  → для каждого текстового сообщения:
      определить user_id по маппингу из экспорта
      INSERT note (tg_message_id = NULL, created_at = дата из экспорта,
                   chat_id = целевая группа, is_group = true)
      enqueue process_note
  → прогресс и отчёт по пропущенным
```

`tg_message_id = NULL` сознательно: id из экспорта не совпадают с теми, что
бот увидит позже, и уникальный индекс на них ставить нельзя. Защита от
повторного импорта - отдельный ключ идемпотентности в `structured`
(`{"import_id": "..."}`) и проверка перед вставкой.
